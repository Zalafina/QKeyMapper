# QKeyMapper MCP Review 与优化建议

评审与整理日期：2026-10-24。

**用户已确认的首要约束：MCP 是为 QKeyMapper 锦上添花的增强功能；必要的公共引擎小改动必须独立验证，证明原有功能和性能没有退化后再接入。** 用户选择的路线是“必要小改动独立验收”，不要求首版完全冻结输入引擎，也不以本次接入为由进行全局配置模型或映射引擎重写。

本文是[唯一主计划](qkeymapper_mcp_automation_plan_codex.md)的评审附件，供后续会话优化计划使用，不建立第二份任务进度来源。能力覆盖仍见[能力与等价性矩阵](capability_matrix.md)，产品历史验收仍见[验证记录](validation.md)。以下整改方向尚未实施；本次授权和交付仅为新增本文档，不修改产品代码、原主计划或既有验收结论。

原方案中值得保留的设计包括：官方 SDK 桥接、受控本机 IPC、产品端鉴权、GUI／MCP 共用业务操作、明确来源引用、预览后提交，以及区分修改、保存和实际生效。现有身份核验、权限和失败保护有实际用途，不应仅为减少代码量而删除。当前尚未开放的编辑、保存和启停能力属于开发中范围，不作为代码缺陷。

**外部 Agent／回归脚本 → MCP 桥接 → 受控本机 IPC → 共用业务操作 → 现有配置、界面与映射引擎。**

当前主要需要改善的是接入顺序、对原功能的影响边界，以及 Agent 能否可靠理解结果和恢复失败。下文分别标记已复现问题、源码事实和待测风险，不能将风险项写成已证实的崩溃或性能退化。

## 2. 已核实的问题与风险

### R1. 请求执行前取消，会使桥接持续处于忙状态〔P2，已复现〕

**位置与职责：** [bridge.py](../../mcp_bridge/src/qkeymapper_mcp/bridge.py) 的 `_submit()`（48–70 行）、`_call()`（153–161 行）和 `_close_connection()`（191–196 行）。行号对应上述审阅 HEAD，接续时优先按符号定位。

**触发与问题：** `_submit()` 在提交原生工作项时置 `_busy=true`；`asyncio.wrap_future()` 的取消可以传递给尚未开始执行的工作项。若该工作项在执行前被取消，`run()` 不会进入，负责清除 `_busy` 的 `finally` 也不会执行。随后断开路径只清除 `_closing`，无法恢复该忙状态。

本聊天的只读评审阶段使用可控线程调度探针：先阻止执行器取出业务工作项，再创建查询并取消，最后释放执行器。观察结果为：

```text
after_cancel {'status': 'disconnected', 'busy': True}
next_read {'ok': False, 'error': 'busy_or_closed'}
after_disconnect {'status': 'disconnected', 'busy': True}
next_connect_accepted False
```

这是受控调度下对真实 `Bridge` 的复现，不是已经在真实产品配对场景中捕获同一取消时序。探针没有连接 QKeyMapper、读写配对凭据或发送系统输入。

**最小修正方向：** 让作业的取消、完成与忙状态释放具有统一归属，覆盖“尚未执行”和“执行中”两种情况；同时避免旧请求的迟到取消影响下一请求。不能简单提前清除 `_busy`，否则可能让新的 I/O 与旧请求清理重叠。原生 I/O 取消后仍须完成必要排空，再释放借用资源。

**保留问题的影响：** 一次取消可能使该桥接进程后续查询和连接持续被拒绝，用户只能重启桥接，削弱连续自然语言操作的可靠性。

**针对性验收：** 将上述调度条件纳入现有桥接测试。取消后忙状态可恢复，下一查询／连接可以执行，无需重启桥接；同时覆盖执行中取消和紧接着的新请求，确认没有并行 I/O 或旧取消污染新作业。

### R2. 业务失败被包装为 MCP 成功结果〔P2，已通过正式 stdio 路径确认〕

**位置与职责：** [工具封装](../../mcp_bridge/src/qkeymapper_mcp/__main__.py) 的 `Tool.from_function(..., structured_output=True)` 和 `qkm_get_state()`，以及 [bridge.py](../../mcp_bridge/src/qkeymapper_mcp/bridge.py) 的 `_request()` 错误处理（173–177 行）。

**触发与问题：** 本聊天使用正式 SDK 客户端启动当前 stdio 桥接，在没有连接产品时调用 `qkm_get_state`，实际结果为：

```text
stdio_tools 7
is_error False
structured_content {'ok': False, 'error': 'not_connected'}
```

这里 `is_error` 是 SDK 属性名，对应 MCP 的 `isError`。业务失败作为普通字典交给 SDK，工具结果仍被标为成功。另一方面，桥接收到 C++ 的 `error.code`／`error.message` 后，只保留错误码。对于 `context_busy`、陈旧引用或权限不足，Agent 得不到足够的修正指引。

**最小修正方向：** 在 MCP 边界统一转换工具调用的业务失败，返回 `isError=true`，保留受控的错误码、解释和可执行下一步；不要将未经约束的内部异常或私人映射文本直接透出。查询“某个异步操作已经失败”仍然可以是成功的查询，需要与工具调用本身失败区分。该处理符合 [MCP 工具错误语义](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling)。

**保留问题的影响：** 通用客户端不能统一依靠 MCP 错误标志识别失败；Agent 只能额外猜测私有结果结构，错误恢复和用户反馈容易不一致。

**针对性验收：** 正式 SDK／stdio 路径检查未连接、业务拒绝、过期目标等调用失败的 `isError` 与结构化错误一致，并能提供下一步。正常状态查询及“成功查得失败 operation”的结果保持正确语义。同步调整现有测试，避免把当前错误封装方式固化为期望行为。

### R3. MCP 关闭时也会经过新增引擎逻辑〔合并前重点风险，尚未证明性能退化〕

**位置与职责：** [输入修订同步](../../QKeyMapper/qkm_mapping_source_access.h) 的 `observeRuntimeLifecycle()`、[发送与输入入口](../../QKeyMapper/qkeymapper_worker.cpp) 的 `sendInputKeys()`／发送包装／任务构造及 Hook 回调、[GUI 停止协调](../../QKeyMapper/qkeymapper.cpp) 的 `beginMappingStop()`／`finishMappingStop()`。

**源码事实：** 当前改动包括输入回调计数、排队任务存续标记、发送入口互斥，以及公共 GUI 停止流程的改变。它们不以 MCP 是否启用为条件，因此关闭监听不能证明原有映射不受影响。自动化接口关闭、未连接和正在查询，是必须分别检查的状态。

这些改动中包含必要的生命周期安全修复，应逐项说明必要性，并形成独立的验证与提交边界。**不建议简单用 MCP 开关切换两套停止语义，也不能为了减少开销移除必要的安全守卫。**

**最小改善方向：** 在继续扩大能力前，补齐原有映射的独立回归和普通 Release 性能对照；区分公共安全机制与仅为自动化服务的观测成本。自动化专用的快照、哈希、序列化及诊断处理尽量退出输入热路径。保留必要同步时，给出其保护对象、适用阶段及实测成本。

**保留风险的影响：** 即使从未启用 MCP 的普通用户，也会使用改变后的停止和输入路径。如果只验收 MCP 请求或 NoOp 任务，原有映射的释放、设备行为或延迟退化可能未被发现。此处是影响范围和证据缺口，不是已经证明存在卡顿或崩溃。

**针对性验收：** 以原功能为对象，覆盖停止发送、取消、重复停止、延后回切、快速重启和退出，并验证适用的真实键鼠及设备路径。现有 NoOp 生命周期测试可保留为组件证据，不能代替实际输入效果和性能结论。

### R4. 分页查询仍反复构造整个源快照〔P2，源码确认，耗时未测量〕

**位置与职责：** [源快照采集](../../QKeyMapper/qkeymapper.cpp) 的 `collectAutomationSourceSnapshot()`／`handleAutomationSourceQuery()`（37293／37353 行），以及[分页与哈希](../../QKeyMapper/automation/qkm_source_snapshot.cpp) 的 `querySourceSnapshot()`。

**触发与问题：** 在当前初始静止门禁允许查询时，每次源查询都会遍历全部源表、生成完整字段并序列化；随后再次序列化快照以检查大小和计算修订。即使只查询源表目录或一小页，也承担全量开销。部分参数错误还在采集之后才被拒绝。当前 4 MiB 快照上限和响应帧上限约束了数据规模，不能证明 GUI 响应和锁占用开销合适。

**分步改善方向：**

- 先校验参数，再访问源数据。
- 将目录元数据与完整行详情分开，避免目录查询被无关行内容的体积和处理成本牵连。
- 安全复制期间只做必要工作，避免在保护源数据的锁内进行 JSON 编码；后续处理只能使用已安全复制的数据，不能携带仍可变的源指针。
- 在变更失效规则可靠后，为一次分页读取复用有界快照；明确采样时间、引用范围和失效语义。若改变原先逐页重新核验的契约，需同步接口说明与回归，不能静默改变含义。
- 查询增加执行预算和限流，不能只限制响应字节数。

不得直接用现有结构代次替代完整内容校验，也不得让缓存引用自动成为编辑许可。

**保留问题的影响：** 较大配置、多页读取或 Agent 连续重试会重复占用 GUI 线程和源数据保护区；本次未测量实际耗时，不据此宣称已发生性能退化。

**针对性验收：** 使用正常及接近当前上限的合成配置，比较目录、单页、多页和错误请求的处理成本与 GUI 响应。覆盖读取期间的 GUI 修改、重排、加载和权限变化，确认数据一致性与陈旧引用拒绝仍然成立。

## 3. 建议的后续实现路线

### 3.1 先建立原有功能不退化的基线

把当前改动区分为公共安全修复、自动化适配和开发测试设施，分别记录影响与证据。已存在的相关提交可作为独立审阅起点，不为整理分类而重写已有提交历史。

公共停止协调保留单一实现，独立验证取消、重复停止、停止发送、延后回切、快速重启和退出。自动化专用的查询、哈希及诊断处理尽量退出输入热路径。暂不进行全局配置模型或映射引擎重写。

安全读取和写入仍须以真实生命周期边界为依据。不能用固定延时、单个状态位、零计数或只在 MCP 侧加锁，替代原 GUI／Worker 共享状态的正确性。

### 3.2 优先完成一个真实可用的操作闭环

在必要生命周期边界可靠后，完成：

**发现能力 → 查询目标 → 预览 A→B → 提交 → 显式保存 → 冷启动读回 → 按用户意图开始 → 验证 → 停止。**

首个闭环同时包含取消、冲突、过期预览、保存失败和断线后的结果查询。修改默认保持停止，保存报告明确范围，避免误保存用户其他草稿。运行中需要停止后修改时，继续遵循原计划的用户选择、等待清理及重新校验要求。

请求去重、异步操作结果和断线恢复应随首个写入能力完成，不能留到大量写接口接入之后。业务 operation 与单次传输请求应分别识别；超时或断线后先查询原结果，不能盲目重新追加、保存或执行停止动作。

保留原计划的完整功能目标；后续以“一个功能从 GUI 到持久化和运行效果全部打通”为单位扩展。每个切片既检查 GUI／MCP 等价，也检查独立业务预期，避免两条路径共同出错却因结果相同而通过。

### 3.3 让接口足以支撑自然语言操作

仅提供新增、查询、修改、删除接口和字段名，还不足以帮助不熟悉 QKeyMapper 的用户。首个闭环就应提供：

- 可查询的按键名称、参数范围、单位、默认值、依赖和典型示例。
- 可解释的冲突与拒绝原因，并给出合法的下一步或选择。
- 当前目标、配置来源、允许操作和受阻条件；这些信息复用实际业务守卫。
- 面向用户的变更摘要，同时提供机器可核对的结构化结果。

自然语言理解仍由外部 Agent 完成；复用现有键串解析和校验，不再建立一套不同语义的映射语言。Skill 是辅助指南，基础使用不依赖特定 Agent 或 Skill。能力说明应随功能接入维护，未实现或未验证的能力不得混入可用能力列表。

使用代表性的自然语言需求验证最终结果，例如“在指定配置里把 A 改为 B”“只改这条映射的备注”“解释为何当前映射没有生效”。验收关注实际业务状态、必要澄清和副作用边界，不要求不同 Agent 产生完全相同的工具调用顺序。

### 3.4 保持一个业务实现，分离配置与运行观测

GUI 与 MCP 收集参数后进入同一业务入口，按能力逐步提取必要逻辑，不为全部控件建立通用 setter。已有函数能完整承担业务职责时直接复用；仍包含弹窗、焦点、物理修饰键或暂存控件依赖时，只提取该功能必要的校验和提交逻辑。

明确区分：

- 编辑中的配置及其修订。
- 已保存配置及保存结果。
- 当前运行所使用的配置。
- 带采样时间的运行状态。

运行观测不应无意义地使配置预览失效。运行期间无法安全读取的字段，应明确标记不可用；历史快照不得冒充当前状态。沿用实例内引用，首版不修改 INI 增加永久 UUID。

保持主计划中即时显示操作与配置编辑的区别：现有 GUI 允许运行中移动／缩放窗口的操作应保持可用；要求空闲的映射和设置编辑仍须经过同一状态校验。不能通过临时切 Tab、直接写 INI 或只修改控件值完成接入。

### 3.5 让开发诊断尽早服务开发

将最小诊断能力纳入早期闭环：实际配置来源、监视／匹配状态、停止所处阶段、未完成工作以及错误关联信息。这些信息帮助 Agent 区分“尚未匹配”“配置未生效”“等待清理”和“接口失败”，同时服务日常用户的解释需求。

详细事件记录按需启用、有界保留，默认不增加逐输入日志。真实输入、设备及驱动测试继续使用专用权限和明确场景；内部派发成功不能代替目标程序收到输入，组件任务完成也不能代替真实设备释放。

沿用现有传输与鉴权基础。普通用户的连接配置和免 Python 打包应在首个闭环后尽早试用，提前发现安装与授权流程中的障碍；多实例提示按独立切片完成。保留明确目标身份和必要确认，连续操作不反复激活窗口或重复要求已完成的授权。

## 4. 建议优先顺序与验收要求

| 顺序 | 工作 | 完成判据 |
|---|---|---|
| 1 | 桥接可靠性 | 修复 R1、R2；针对性回归和正式 SDK／stdio 错误语义通过 |
| 2 | 公共引擎验收 | 完成 R3 的原功能与性能对照，再扩大引擎改动；必要公共修复可独立审阅、验证和提交 |
| 3 | 首个业务闭环 | 安全读取、编辑、保存、明确启停及结果核验打通；包含失败、取消和重连路径 |
| 4 | 逐项扩展 | 宏、共通映射、设置、界面和开发诊断，每项保留独立 GUI／MCP 对照 |
| 5 | 交付验收 | 覆盖普通用户环境、Win10／Win11、受影响的 Qt5 路径及打包使用；性能证据随受影响实现更新 |

R4 随查询能力完善处理，不以删除安全门禁或放宽引用校验作为性能优化。阶段顺序是给主计划的调整建议；后续会话应将采纳的决定合并到唯一主计划，再按其记录实施，本文不单独维护完成状态。

### 性能与原功能对照

性能对照至少包含以下四种状态，使用相同构建配置和输入场景：

1. 主分支基线。
2. 当前分支 MCP 关闭。
3. MCP 启用但空闲。
4. MCP 持续查询。

使用普通 Release，记录输入延迟分布、CPU、内存、线程／唤醒和 GUI 响应；重复测量以区分环境噪声与稳定退化。不能用接口关闭、计数归零或 NoOp 测试代替性能结论；出现稳定可复现的退化时先处理再发布，不默认接受其成本。
